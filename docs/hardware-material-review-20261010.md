# 大型摆式悬挂麦轮：资料初查

日期：2026-10-10。用户确认实车使用“摆式悬挂麦轮底盘（大型）”。检查对象是共享目录下的 `ROS机器人扩展板/` 和 `ROS机器人小车底盘/`。

## 结论与范围

资料足以准备ROS 2底盘适配及独立驱动联调，暂无必要再收集整套通用ROS课程。当前缺少实物版本与实际配置的确认，现有示例存在需修正的接口/反馈问题，不能把资料齐全等同于已可直接闭环运行。

本轮进行了目录清点、关键Markdown/PDF阅读、串口/CAN协议表读取、SDK/STM32源码压缩包内静态检查、3个关键ROS 2 Python文件的AST解析，以及V3.0接口图与大型底盘安装孔位图的视觉检查。没有安装驱动、运行厂商代码、刷固件、发送电机指令或修改厂商文件；没有逐一观看装配视频或通过CAD求整车几何。

## 2. 已找到的接口

### 主机与控制板

SDK `py_install_V3.3.9.zip` 中 `py_install/Rosmaster_Lib/Rosmaster_Lib.py` 默认使用 `/dev/myserial`、115200波特率。设备绑定规则针对CH340的 `1a86:7523`，真实端口仍需在Ubuntu检查，不能假定已映射成功。

[V3.0简介](../../ROS机器人扩展板/1、扩展板STM32驱动教程/1、扩展板简介/1、扩展板V3.0介绍.pdf)说明micro USB用于通信，type-C用于供电；V2/V3说明要求Python库V3.3.X或以上。资料包含V3.3.9库，但实际安装版本未知。硬件板版本、Python库版本与固件版本是不同编号。

[V2/V3通信协议表](../../ROS机器人扩展板/8、硬件资料/通讯协议/Rosmaster扩展板与主控板通信协议_V2_V3.xlsx)含串口与CAN两个工作表。串口协议提供车型设置、运动命令、速度/IMU/编码器反馈及固件版本查询，可作为必要的C++通信适配依据。

### ROS 2链路

资料中的 `Mcnamu_driver_X3.py` 订阅 `geometry_msgs/msg/Twist` 的 `cmd_vel`，把 `linear.x`、`linear.y`、`angular.z`传给 `set_car_motion(vx, vy, angular)`。发布 `vel_raw`、`/imu/data_raw`、`/imu/mag`、`voltage`、`edition` 等。

`base_node_X3.cpp` 接收 `vel_raw`，积分得到 `/odom_raw`。提供的 `robot_localization.zip` 含 `ekf_x1_x3_launch.py` 和 `ekf_x1_x3.yaml`，把滤波输出重映射到 `/odom`，设置 `odom`、`base_footprint`并发布TF。

因此当前C++跟随控制可通过ROS 2话题与底盘驱动连接。资料中的底盘通信节点主要为Python、原始里程计节点为C++，可以先复用；若项目要求通信驱动也全部C++，协议资料支持后续独立适配，但本轮未实施。

## 3. 接入前需要处理的具体问题

1. **普通X3与大型车型不能混用。** 协议表 `串口协议!P49` 列出X3=1、X3PLUS=2。STM32 `app_motion.h` 标注 `CAR_MECANUM_MAX=2` 为“大架构大麦轮 X3 PLUS”；大型安装板文件使用“X3 PRO”命名，说明需要核对命名与实物配置。现有ROS 2示例在 `Mcnamu_driver_X3.py:33` 写死 `set_car_type(1)`，SDK该调用含永久保存标志。不能未经核对直接用该示例替大型车设置车型。
2. **横向里程计速度被覆盖。** `base_node_X3.cpp:116`先写入测得的 `linear.y`，下一行又将其设为0。全向横移时会给状态估计发送错误的速度约束，需适配后检查横移与融合结果。
3. **反馈新鲜度没有随串口帧保留。** SDK `get_motion_data()`返回缓存值；ROS驱动每0.1秒读取缓存并使用当前主机时间发布IMU，原始里程计又使用当前时间积分。所查代码没有以最近有效串口帧的接收时间判断反馈是否失效，不能用持续有ROS消息证明控制板仍在更新。
4. **命令断联停车尚未确认。** 所查ROS驱动没有速度命令接收超时后定时归零的逻辑。所查V3.5.1固件包含零速度命令制动、低电压/复位/遥控相关停止路径，但未确认通用USB串口速度命令失联超时机制。源码存在IWDG相关代码，也不能据此判定主机停止发命令时一定停车。需要匹配实物固件并进行架空轮子的停发/断联验证；若缺少保护，补相应驱动与固件能力。
5. **启动默认带另一速度发布者。** X3 launch启动 `yahboom_joy_X3`，该节点也发布 `cmd_vel`。自动跟随联调应禁用或通过明确的仲裁接入，保持最终速度来源明确。
6. **ROS发行版和安装细节需适配。** 包中有Humble教程，但功能包文档仍出现Foxy依赖命令；不能原样执行。使用当前Ubuntu22.04/Humble检查依赖与编译。原始里程计首帧时间差也需初始化和异常间隔检查，不能把静态阅读当作运行通过。

以上是所提供源码的静态发现，不代表已经在实物上复现所有问题。3个关键Python文件AST解析通过；ROS依赖、C++编译、串口和实际运动尚未验证。

## 5. 后续建议

先核对实物型号及固件，再整理Humble底盘适配，修正车型、反馈、独立超时和启动发布链。随后架空轮子验证四个电机的前进/转向/横移方向，检查真实odom及实际停车，再安装D435i并做空场低速跟随。

第一版可先令 `linear.y=0`，用前进与车身转向复用已有跟随逻辑，实车轮速仍由正确的麦轮运动学处理；全向横移的跟随策略之后单独扩展和验证。已通过的差速仿真保留为基线，不能宣布它已验证大型麦轮实车。
